# Migrating internal 1.x integrations

The public 2.0 line is a major release. Do not replace an internal 1.x dependency without reviewing the client and backend together. Production consumers continue to use their private versions until explicitly migrated.

1. Use ESM and Node 22 or later. Require Zod 4 and import `/client` in browser code, `/server` in backend code, and `/schemas` for shared contracts. Remove CommonJS assumptions and imports of undocumented internal paths.
2. Configure Telegram verification through `initDataConfig`. HMAC requires the bot token; Ed25519 requires the bot ID. Use the appropriate production/test environment and an explicit application namespace. Freshness cannot be disabled: its range is 1 second to 7 days. Default user validation requires a positive safe-integer ID and `first_name`. Only opt out of requiring a user for non-user launch contexts.
3. Provision a 32-byte encryption key and durable shared group/replay stores. `tokenGroupStore` requires `get` and atomic `incr`; missing state is `null`. `replayStore.consume` must be atomic and retain markers until the supplied expiry. Preserve refresh counters without TTL or eviction. If revocation is disabled, that choice must be explicit.
4. Plan for fresh authentication. Versioned JWE credentials are scoped by purpose, namespace, bot, and environment and intentionally do not accept old token formats. Changing key or scope invalidates existing credentials. Coordinate client rollout, cookie/cache clearing, and session handling instead of trying to reuse old encrypted tokens.
5. The browser uses memory-only storage by default. Explicitly pass an adapter and storage key if persistent access caching is required. Refresh credentials stay in cookies; neither raw init-data nor refresh tokens belong in the cache. Existing cache keys are not imported automatically.
6. Keep the shared SUCCESS/statusCode=200 envelope even with custom response schemas. ISO or millisecond expiries are accepted, but manual commits must be unexpired. App-session payloads are objects; the client injects configured clientVersion and resolves init-data only when those fields are absent. A cold-start refresh body is now passed as `{ payload, schema }` in the third argument of `getAccessToken`.
7. Review cookie adapters: set takes an options object; clear receives the name and matching attributes; both are awaited. MaxAge is seconds. Server `init` caches only the same config object; `create` always creates an independent verifier. Keep config objects stable and treat initialized schemas/configuration as immutable.
8. Evaluate optional single-use behavior against the launch/resume UX. It defaults to false. With it enabled, repeated init-data exchanges are rejected until the assertion expires; resume using a valid refresh cookie. Group invalidation affects all refresh sessions for an identity and does not revoke access tokens immediately.

Before public distribution, review shared changes for any private production backports and coordinate security-sensitive fixes. This repository does not modify, deploy, or automatically upgrade those consumers. Run the repository checks and application integration tests before rollout.
